Authentication & Authorization at Scale

A comprehensive guide to building secure, scalable identity systems used by billions of users worldwide

Overview

Modern applications handle authentication and authorization for millions to billions of users across distributed systems. This guide covers the patterns, trade-offs, and implementation strategies used by companies like Google, Meta, Amazon, and Netflix.

Key Principles

  • Zero Trust: Never trust, always verify - every request must be authenticated and authorized
  • Least Privilege: Grant minimum permissions necessary for each task
  • Defense in Depth: Multiple layers of security controls
  • Separation of Concerns: Decouple authentication from authorization
Why This Matters

At scale, authentication becomes a bottleneck, authorization decisions must be consistent across services, and security breaches can affect millions of users. The patterns in this guide are battle-tested at companies handling 100,000+ auth requests per second.

Core Concepts

Authentication (AuthN)

Question: "Who are you?"

Verifying identity through credentials:

  • Something you know (password)
  • Something you have (token, device)
  • Something you are (biometric)

Authorization (AuthZ)

Question: "What can you do?"

Verifying permissions based on:

  • Identity (who you are)
  • Context (where, when, how)
  • Resource (what you're accessing)

Authentication Models

Session-Based

Server creates session after login, stores session ID in cookie. Stateful - server tracks active sessions.

Stateful

Pros: Immediate revocation, server control

Cons: Session store bottleneck, scaling challenges

Token-Based (JWT)

Server issues signed token with claims. Client sends token with each request. Stateless validation.

Stateless

Pros: Scales horizontally, no session storage

Cons: Cannot revoke before expiry, larger payload

OAuth 2.0 / OIDC

Delegated authorization with identity layer. User authenticates with provider, app receives scoped tokens.

Delegated

Pros: Industry standard, third-party integration

Cons: Complex flow, redirect overhead

API Keys

Static secret in request header. Simple machine-to-machine authentication.

Long-lived

Pros: Simple, easy to manage

Cons: No user context, security risk if compromised

Authorization Models

Model Concept Best For Complexity
RBAC User → Role → Permission Enterprise apps, clear hierarchies Low
ABAC Attributes (user, resource, environment) Fine-grained, context-aware access High
PBAC Policy-as-code (OPA, Cedar) Complex business rules, compliance High
ReBAC Relationships (owner, viewer, editor) Social apps, collaborative systems Medium

Implementation Patterns

JWT Authentication Flow

// Backend: Express.js + JWT
const jwt = require('jsonwebtoken');
const bcrypt = require('bcrypt');

// Login endpoint
app.post('/api/login', async (req, res) => {
  const { email, password } = req.body;
  const user = await db.users.findOne({ email });

  if (!user || !await bcrypt.compare(password, user.passwordHash)) {
    return res.status(401).json({ error: 'Invalid credentials' });
  }

  const token = jwt.sign(
    { sub: user.id, role: user.role },
    process.env.JWT_SECRET,
    { expiresIn: '1h', issuer: 'auth-service' }
  );

  res.json({ accessToken: token });
});

// Auth middleware
function authenticate(req, res, next) {
  const authHeader = req.headers.authorization;
  if (!authHeader?.startsWith('Bearer ')) {
    return res.status(401).json({ error: 'Missing token' });
  }

  try {
    const payload = jwt.verify(
      authHeader.slice(7),
      process.env.JWT_SECRET
    );
    req.user = payload;
    next();
  } catch (err) {
    res.status(401).json({ error: 'Invalid token' });
  }
}

RBAC Authorization Middleware

const ROLES = {
  ADMIN: 'admin',
  EDITOR: 'editor',
  VIEWER: 'viewer'
};

function authorize(...requiredRoles) {
  return (req, res, next) => {
    if (!req.user || !requiredRoles.includes(req.user.role)) {
      return res.status(403).json({
        error: 'Insufficient permissions'
      });
    }
    next();
  };
}

// Usage
app.get('/api/admin/users',
  authenticate,
  authorize(ROLES.ADMIN),
  async (req, res) => {
    const users = await db.users.find();
    res.json(users);
  }
);

OAuth 2.0 with PKCE

// Frontend: React OAuth2 flow with PKCE
function generateCodeVerifier() {
  const array = new Uint8Array(32);
  crypto.getRandomValues(array);
  return btoa(String.fromCharCode(...array))
    .replace(/[^a-zA-Z0-9]/g, '');
}

async function generateCodeChallenge(verifier) {
  const encoder = new TextEncoder();
  const data = encoder.encode(verifier);
  const digest = await crypto.subtle.digest('SHA-256', data);
  return btoa(String.fromCharCode(...new Uint8Array(digest)))
    .replace(/\+/g, '-')
    .replace(/\//g, '_')
    .replace(/=/g, '');
}

export function useOAuth2() {
  const [verifier, setVerifier] = useState(null);

  const initiateLogin = async () => {
    const codeVerifier = generateCodeVerifier();
    const codeChallenge = await generateCodeChallenge(codeVerifier);
    setVerifier(codeVerifier);

    const params = new URLSearchParams({
      client_id: 'my-app',
      redirect_uri: window.location.origin + '/callback',
      response_type: 'code',
      code_challenge: codeChallenge,
      code_challenge_method: 'S256',
      scope: 'openid profile email'
    });

    window.location.href =
      `https://auth-provider.com/authorize?${params}`;
  };

  return { initiateLogin, verifier };
}

Trade-offs

JWT vs Session-Based Authentication

Aspect JWT Session
State Stateless Stateful
Scaling Horizontal, no shared state Requires session store
Revocation Cannot revoke before expiry Immediate revocation
Payload Size 1-3KB (contains claims) Session ID only
Offline Support Yes (self-contained) No (requires server)
Security Token theft risk (XSS) Session fixation risk

RBAC vs ABAC

RBAC

When to use:

  • Clear organizational hierarchy
  • Fixed permission sets
  • Simple admin/user distinction

Limitations:

  • Role explosion with many combinations
  • Cannot express resource-level permissions
  • Coarse-grained

ABAC

When to use:

  • Complex permission logic
  • Context-dependent access
  • Fine-grained control needed

Limitations:

  • Complex policy management
  • Performance overhead
  • Difficult to audit
Common Pitfalls
  • Long-lived JWT without refresh: Cannot revoke compromised tokens. Use 15-minute access tokens with refresh rotation.
  • Storing secrets in JWT payload: Tokens are base64, not encrypted. Never put sensitive data in claims.
  • Client-side only authorization: Always validate server-side. Client checks are for UX only.
  • RBAC with 100+ roles: Role explosion. Switch to ABAC or simplify permission model.
  • Missing state parameter in OAuth: Enables CSRF attacks. Always include and validate state.

Scalability

Scaling Challenges

1K Users

What works:

  • Simple username/password
  • JWT in localStorage
  • Single database
  • Basic RBAC

What breaks:

  • No MFA protection
  • No audit logging
  • Token revocation difficult

1M Users

What breaks:

  • Single database bottleneck
  • JWT secret rotation
  • Password hashing CPU load
  • Brute force attacks

Solutions:

  • Redis cluster for sessions
  • Short-lived tokens + refresh
  • Rate limiting at gateway
  • MFA implementation

1B Users

What breaks:

  • Global latency
  • JWT signing bottleneck
  • Token revocation at scale
  • Compliance complexity

Solutions:

  • Geo-distributed auth
  • Database sharding
  • Edge authentication
  • HSM for key management
  • Passwordless (WebAuthn)

Caching Authorization Decisions

// Cache permission checks
const cache = new Map();

async function checkPermission(userId, resource, action) {
  const cacheKey = `${userId}:${resource}:${action}`;

  if (cache.has(cacheKey)) {
    return cache.get(cacheKey);
  }

  const allowed = await evaluatePolicy(userId, resource, action);

  // Cache for 5 minutes
  cache.set(cacheKey, allowed);
  setTimeout(() => cache.delete(cacheKey), 300000);

  return allowed;
}

Failure Modes

Common Failure Scenarios

1. Token/Session State Failures

  • Token expiration race conditions: Tokens expire mid-request during high load
  • Distributed session inconsistency: Session state diverges across auth servers
  • Token revocation propagation delays: Revoked tokens remain valid in cache
  • Clock skew: Time drift between servers causes validation failures

2. Infrastructure Failures

  • Auth service unavailability: Centralized auth becomes single point of failure
  • Database connection exhaustion: Auth DB overwhelmed during traffic spikes
  • Cache stampede: Simultaneous cache misses overwhelm backend
  • Network partitions: Split-brain scenarios in distributed auth

3. Security Attacks

  • Credential stuffing: Automated attacks with breached credentials
  • Token replay attacks: Captured tokens reused across services
  • Session fixation: Attackers pre-set session IDs before authentication
  • Privilege escalation: Bugs in authorization logic grant unauthorized access

Resilience Patterns

Circuit Breaker for Auth Services

// Circuit breaker implementation
const circuitBreaker = {
  failures: 0,
  lastFailureTime: 0,
  state: 'CLOSED', // CLOSED, OPEN, HALF_OPEN

  async execute(fn) {
    if (this.state === 'OPEN') {
      if (Date.now() - this.lastFailureTime > 30000) {
        this.state = 'HALF_OPEN';
      } else {
        throw new Error('Circuit breaker open');
      }
    }

    try {
      const result = await fn();
      this.onSuccess();
      return result;
    } catch (error) {
      this.onFailure();
      throw error;
    }
  },

  onSuccess() {
    this.failures = 0;
    this.state = 'CLOSED';
  },

  onFailure() {
    this.failures++;
    this.lastFailureTime = Date.now();
    if (this.failures >= 5) {
      this.state = 'OPEN';
    }
  }
};

Graceful Degradation

// Tiered authentication fallback
async function authenticateRequest(req) {
  try {
    // Tier 1: Full authentication
    return await validateToken(req.headers.authorization);
  } catch (error) {
    try {
      // Tier 2: Cached authentication
      const cached = await getCachedAuth(req.user?.id);
      if (cached && !isExpired(cached)) {
        return cached;
      }
    } catch (cacheError) {
      // Tier 3: Read-only mode
      if (req.method === 'GET') {
        return { mode: 'read-only', user: null };
      }
    }

    // Tier 4: Service unavailable
    throw new ServiceUnavailableError('Auth service down');
  }
}
Emergency Access Procedure

When complete auth system failure occurs:

  1. Activate break-glass accounts (require 2-admin approval)
  2. Log all emergency access with detailed audit trail
  3. Time-limit access to 1 hour maximum
  4. Automatic revocation after timeout
  5. Post-incident review within 24 hours

// Structured logging for auth events
function logAuthEvent(event, data) {
  const logEntry = {
    timestamp: new Date().toISOString(),
    level: 'INFO',
    event: event,
    userId: data.userId,
    ipAddress: data.ip,
    userAgent: data.userAgent,
    success: data.success,
    latency: data.latency,
    requestId: data.requestId,
    traceId: data.traceId
  };

  // Never log sensitive data
  delete logEntry.password;
  delete logEntry.token;

  logger.info(JSON.stringify(logEntry));
}

Chaos Engineering

Failure Injection Tests

  • Kill auth service randomly: Verify graceful degradation
  • Inject network latency: Test timeout handling
  • Corrupt cache: Verify fallback to database
  • Rotate keys mid-flight: Test key rotation handling
  • Simulate clock skew: Test token validation with time drift
  • Flood with invalid tokens: Test rate limiting

Security Testing

Penetration Testing Checklist

  • Attempt authentication bypass with malformed tokens
  • Test for IDOR (Insecure Direct Object Reference)
  • Verify privilege escalation is not possible
  • Test session fixation vulnerabilities
  • Attempt token replay attacks
  • Test for mass assignment vulnerabilities
  • Verify rate limiting prevents brute force
  • Test CSRF protection on state-changing operations

Future Trends

2026-2027: Near-term

  • Passkeys become default: New applications default to FIDO2/WebAuthn, passwords become opt-in legacy
  • OAuth 2.1 finalized: Industry-wide adoption, OAuth 2.0 flows deprecated
  • AI-powered threat detection: Standard feature in IdPs, detecting account takeover in real-time
  • Zero Trust maturity: Continuous verification, micro-segmentation standard for enterprise

2027-2028: Mid-term

  • Decentralized identity pilots: Enterprise adoption for employee credentials, supply chain
  • Quantum-safe hybrid crypto: New systems deploy hybrid TLS, dual-signed tokens
  • Behavioral biometrics mainstream: Continuous auth standard for financial, healthcare apps
  • Privacy-preserving auth: Zero-knowledge proofs for age verification without data exposure

2028-2030: Long-term

  • Passwordless world: Passwords deprecated, legacy systems bridge to passkeys/certificates
  • Post-quantum migration complete: Critical systems migrated to PQC, classical crypto deprecated
  • Self-sovereign identity: Users control identity across applications, portable credentials
  • AI vs AI security: Adversarial AI attacks met with defensive AI, continuous arms race

Emerging Technologies

Decentralized Identity (DID)

Users control their own identity credentials without central authorities. W3C DID specification gaining traction.

Impact: Reduced IdP dependency, privacy-preserving authentication, portable identity

Quantum-Resistant Cryptography

NIST PQC standards: CRYSTALS-Kyber (key encapsulation), CRYSTALS-Dilithium (signatures). Transition needed by 2030.

Action: Inventory crypto assets, design for crypto-agility, start hybrid deployment

Continuous Authentication

Behavioral biometrics (keystroke dynamics, mouse patterns) for continuous verification throughout session.

Benefit: Detect session hijacking mid-stream, frictionless security

Verifiable Credentials

Digital credentials (degrees, certifications) that can be presented cryptographically without revealing unnecessary data.

Use case: Prove you're over 18 without revealing birthdate

Migration Checklist

From OAuth 2.0 to 2.1:

  • Replace Implicit flow with Authorization Code + PKCE
  • Remove Resource Owner Password Credentials flow
  • Implement PKCE for all clients (including confidential)
  • Add DPoP for refresh token binding
  • Deploy PAR for authorization requests
  • Reduce access token lifetime to 15 minutes or less
  • Implement refresh token rotation

From Passwords to Passwordless:

  • Add FIDO2/WebAuthn support
  • Implement passkey enrollment flow
  • Design account recovery mechanism
  • Provide fallback for devices without biometrics
  • Test cross-device authentication

Security System Design

A comprehensive guide from fundamentals to advanced security architecture for modern distributed systems

Overview

Security in system design is not an afterthought—it's a foundational architectural concern that must be woven into every layer of your system. This guide covers the complete spectrum of security considerations, from basic principles to advanced threat modeling and incident response.

Core Security Principles

  • Zero Trust: Never trust, always verify—every request must be authenticated and authorized
  • Defense in Depth: Multiple layers of security controls to prevent single points of failure
  • Least Privilege: Grant only the minimum permissions necessary for each component
  • Assume Breach: Design systems assuming attackers are already inside the network
  • Fail Secure: When systems fail, they should default to a secure state

Security Fundamentals

The CIA Triad

The foundation of all security design rests on three pillars:

Confidentiality

Ensure data is accessible only to authorized parties.

  • Encryption (at rest and in transit)
  • Access controls
  • Data classification
  • Secure communication channels

Integrity

Ensure data cannot be modified by unauthorized parties.

  • Digital signatures
  • Hash verification
  • Checksums
  • Audit logging

Availability

Ensure systems and data are accessible when needed.

  • Redundancy
  • DDoS protection
  • Disaster recovery
  • Rate limiting

Authentication vs Authorization

Aspect Authentication (AuthN) Authorization (AuthZ)
Question Who are you? What can you do?
Purpose Verify identity Verify permissions
Timing First (login) After authentication
Examples Passwords, MFA, biometrics RBAC, ABAC, ACLs
Failure Access denied (401) Forbidden (403)

Security by Design Principles

  1. Economy of Mechanism: Keep security designs simple and small
  2. Fail-Safe Defaults: Base access decisions on permission rather than exclusion
  3. Complete Mediation: Check every access to every object, not just at entry
  4. Open Design: Security should not depend on secrecy of design (Kerckhoffs's principle)
  5. Separation of Privilege: Require multiple conditions for access
  6. Least Common Mechanism: Minimize shared resources
  7. Least Privilege: Every program and user should operate with minimal privileges

Authentication

Authentication Methods

Something You Know

  • Passwords: Must be hashed with bcrypt/scrypt/Argon2
  • PINs: Short numeric codes
  • Security Questions: Weak, easily guessable

Strengths: Simple, familiar

Weaknesses: Phishing, brute force, credential stuffing

Something You Have

  • TOTP: Time-based one-time passwords (Google Authenticator)
  • Hardware Tokens: YubiKey, FIDO2 devices
  • SMS Codes: Vulnerable to SIM swapping

Strengths: Resistant to phishing

Weaknesses: Device loss, SIM swapping (SMS)

Something You Are

  • Fingerprint: Touch ID, Android fingerprint
  • Face Recognition: Face ID, Windows Hello
  • Iris Scan: High security applications

Strengths: Convenient, hard to forge

Weaknesses: Privacy concerns, false positives

Passwordless / FIDO2

  • WebAuthn: W3C standard for passwordless auth
  • Passkeys: Platform authenticators (iCloud, Google)
  • Biometric + Device: Combined factors

Strengths: Phishing-resistant, user-friendly

Weaknesses: Device dependency, adoption

Multi-Factor Authentication (MFA)

Combining two or more authentication factors dramatically increases security:

// MFA implementation example
async function authenticateWithMFA(username, password, totpCode) {
  // Step 1: Verify password
  const user = await findUser(username);
  const passwordValid = await bcrypt.compare(password, user.passwordHash);

  if (!passwordValid) {
    throw new AuthenticationError('Invalid credentials');
  }

  // Step 2: Verify TOTP
  const totpValid = verifyTOTP(user.totpSecret, totpCode);

  if (!totpValid) {
    throw new AuthenticationError('Invalid MFA code');
  }

  // Step 3: Check for suspicious activity
  const riskScore = await assessRisk(user, requestContext);
  if (riskScore > THRESHOLD) {
    await challengeUser(user, 'additional_verification');
  }

  // Step 4: Issue session
  return createSession(user);
}

Password Storage Best Practices

Never Store Passwords in Plaintext

// WRONG - Never do this
const user = {
  username: 'alice',
  password: 'mysecretpassword123' // NEVER STORE LIKE THIS
};

// RIGHT - Use bcrypt with salt rounds
const bcrypt = require('bcrypt');
const SALT_ROUNDS = 12;

async function hashPassword(password) {
  const salt = await bcrypt.genSalt(SALT_ROUNDS);
  return bcrypt.hash(password, salt);
}

async function verifyPassword(password, hash) {
  return bcrypt.compare(password, hash);
}

Authorization

Authorization Models

Role-Based Access Control (RBAC)

Permissions assigned to roles, users assigned to roles.

// RBAC example
const roles = {
  admin: ['user:read', 'user:write', 'user:delete'],
  editor: ['user:read', 'user:write'],
  viewer: ['user:read']
};

function hasPermission(user, permission) {
  const userRoles = getUserRoles(user.id);
  return userRoles.some(role =>
    roles[role]?.includes(permission)
  );
}

Pros: Simple, scalable, easy to manage

Cons: Role explosion, coarse-grained

Attribute-Based Access Control (ABAC)

Permissions based on attributes of user, resource, action, and context.

// ABAC policy example
const policy = {
  effect: 'allow',
  condition: {
    all: [
      { fact: 'user.department', operator: 'equals', value: 'finance' },
      { fact: 'resource.classification', operator: 'in', value: ['public', 'internal'] },
      { fact: 'environment.time', operator: 'between', value: ['09:00', '17:00'] }
    ]
  }
};

Pros: Fine-grained, flexible, context-aware

Cons: Complex, harder to audit

Relationship-Based Access Control (ReBAC)

Permissions based on relationships between subjects and resources.

// ReBAC example (like Google Zanzibar)
const relationships = [
  { subject: 'user:alice', relation: 'owner', resource: 'doc:123' },
  { subject: 'user:bob', relation: 'viewer', resource: 'doc:123' },
  { subject: 'group:engineering', relation: 'member', resource: 'project:abc' }
];

function canAccess(userId, action, resourceId) {
  // Check direct relationships and transitive ones
  return checkRelationship(userId, action, resourceId);
}

Pros: Intuitive, handles complex hierarchies

Cons: Requires relationship database

Policy-Based Access Control (PBAC)

Centralized policies written in declarative languages.

// Open Policy Agent (OPA) policy
package authz

default allow = false

allow {
  input.user.role == "admin"
}

allow {
  input.user.id == input.resource.owner_id
  input.action == "read"
}

allow {
  input.user.department == input.resource.department
  input.resource.visibility == "internal"
}

Pros: Centralized, auditable, version-controlled

Cons: Learning curve, policy management

Choosing the Right Model

Scenario Recommended Model Why
Simple SaaS with user tiers RBAC Easy to implement and understand
Enterprise with complex rules ABAC or PBAC Handles time, location, classification
Collaborative documents (Google Docs) ReBAC Natural fit for ownership/sharing
Multi-tenant platform ABAC + RBAC hybrid Tenant isolation + role management
Microservices architecture PBAC (OPA) Centralized policy, distributed enforcement

Encryption & Cryptography

Encryption Types

Symmetric Encryption

Same key for encryption and decryption.

  • AES-256: Industry standard, fast
  • Use cases: Data at rest, bulk encryption
  • Key management: Must securely distribute keys
const crypto = require('crypto');

function encrypt(text, key) {
  const iv = crypto.randomBytes(16);
  const cipher = crypto.createCipheriv('aes-256-gcm', key, iv);

  let encrypted = cipher.update(text, 'utf8', 'hex');
  encrypted += cipher.final('hex');

  return {
    iv: iv.toString('hex'),
    encrypted,
    tag: cipher.getAuthTag().toString('hex')
  };
}

Asymmetric Encryption

Different keys for encryption and decryption (public/private key pair).

  • RSA: 2048+ bits, widely supported
  • ECC: Smaller keys, faster (secp256k1, P-256)
  • Use cases: Key exchange, digital signatures, TLS
const { generateKeyPairSync } = require('crypto');

const { publicKey, privateKey } = generateKeyPairSync('rsa', {
  modulusLength: 4096,
  publicKeyEncoding: { type: 'spki', format: 'pem' },
  privateKeyEncoding: { type: 'pkcs8', format: 'pem' }
});

Hashing vs Encryption

Aspect Hashing Encryption
Purpose Verify data integrity, store passwords Protect confidentiality
Reversibility One-way (cannot reverse) Two-way (can decrypt with key)
Output Fixed-length hash Variable-length ciphertext
Use Cases Passwords, file checksums, digital signatures Sensitive data, communication
Algorithms bcrypt, Argon2, SHA-256 AES, RSA, ECC

Database Encryption

  id SERIAL PRIMARY KEY,
  email VARCHAR(255) UNIQUE NOT NULL,

VALUES (

-- Decrypt on read
SELECT
  email,
  pgp_sym_decrypt(ssn_encrypted, 'encryption_key') as ssn
FROM users
WHERE id = 1;

Key Management

Key Management Best Practices

  • Never hardcode keys: Use environment variables or secrets managers
  • Rotate keys regularly: Automated rotation every 90 days
  • Use key hierarchy: Master keys encrypt data keys (envelope encryption)
  • Hardware Security Modules (HSM): For high-security applications
  • Key separation: Different keys for different purposes (encryption, signing)
  • Audit key usage: Log all key access and operations

VPN & Zero Trust Networking

// Zero Trust network access pattern
async function authorizeNetworkAccess(userId, resourceId, context) {
  // 1. Verify device posture
  const deviceTrusted = await checkDeviceCompliance(context.deviceId);
  if (!deviceTrusted) {
    throw new Error('Device not compliant');
  }

  // 2. Verify user identity (continuous authentication)
  const userVerified = await verifyUserSession(userId, context);
  if (!userVerified) {
    throw new Error('User verification failed');
  }

  // 3. Check resource access policy
  const allowed = await evaluatePolicy({
    subject: userId,
    action: 'access',
    resource: resourceId,
    context: context
  });

  if (!allowed) {
    throw new Error('Access denied');
  }

  // 4. Establish microsegmented connection
  return establishSecureTunnel(userId, resourceId);
}

Web Application Security

Common Vulnerabilities (OWASP Top 10)

1. Injection (SQL, NoSQL, OS)

Attack: Inject malicious code through user input

// VULNERABLE
const query = `SELECT * FROM users WHERE id = ${userId}`;

// SECURE - Use parameterized queries
const query = 'SELECT * FROM users WHERE id = $1';
await db.query(query, [userId]);

2. Broken Authentication

Attack: Exploit weak authentication mechanisms

  • Weak passwords, no MFA
  • Session fixation
  • Credential stuffing
  • Exposed session tokens

3. Sensitive Data Exposure

Attack: Access unencrypted sensitive data

  • Store passwords in plaintext
  • Transmit data over HTTP
  • Log sensitive information
  • Expose data in error messages

4. XML External Entities (XXE)

Attack: Process malicious XML input

// VULNERABLE
const parser = new DOMParser();
const doc = parser.parseFromString(xmlInput, 'text/xml');

// SECURE - Disable external entities
const parser = new DOMParser();
parser.parseFromString(xmlInput, 'text/xml', {
  noent: false,
  dtd: false
});

5. Broken Access Control

Attack: Access unauthorized resources

  • IDOR (Insecure Direct Object Reference)
  • Privilege escalation
  • Missing function-level access control
  • CORS misconfiguration

6. Security Misconfiguration

Attack: Exploit default settings, open cloud storage

  • Default credentials
  • Unnecessary features enabled
  • Verbose error messages
  • Missing security headers

7. Cross-Site Scripting (XSS)

Attack: Inject malicious scripts into web pages

// VULNERABLE
element.innerHTML = userInput;

// SECURE - Escape output
element.textContent = userInput;

// Or use CSP headers
// Content-Security-Policy: default-src 'self'

8. Insecure Deserialization

Attack: Execute arbitrary code via malicious serialized data

// VULNERABLE
const data = JSON.parse(userInput); // Can execute code

// SECURE - Validate schema
const schema = Joi.object({ name: Joi.string() });
const { error, value } = schema.validate(userInput);
if (error) throw new Error('Invalid input');

9. Using Components with Known Vulnerabilities

Attack: Exploit outdated libraries

  • Run npm audit regularly
  • Use Dependabot/Renovate for updates
  • Monitor CVE databases
  • Remove unused dependencies

10. Insufficient Logging & Monitoring

Attack: Breaches go undetected

  • Log authentication attempts
  • Monitor for anomalies
  • Set up alerts for suspicious activity
  • Retain logs for forensic analysis

API Security

API Authentication Methods

API Keys

Simple token passed in header or query parameter.

// Request with API key
fetch('/api/data', {
  headers: {
    'X-API-Key': 'your-api-key-here'
  }
});

Pros: Simple, easy to implement

Cons: No user context, key leakage risk

Use for: Server-to-server, public APIs

JWT (JSON Web Tokens)

Signed tokens containing user claims.

// JWT structure
{
  "header": { "alg": "HS256", "typ": "JWT" },
  "payload": {
    "sub": "user123",
    "name": "Alice",
    "role": "admin",
    "exp": 1234567890
  },
  "signature": "HMACSHA256(...)"
}

Pros: Stateless, scalable

Cons: Cannot revoke easily, token size

Use for: Stateless APIs, microservices

OAuth 2.0

Delegated authorization framework.

// OAuth 2.0 Authorization Code Flow
// 1. Redirect to authorization server
res.redirect('https://auth.example.com/authorize?' +
  'client_id=YOUR_CLIENT_ID&' +
  'redirect_uri=YOUR_REDIRECT_URI&' +
  'response_type=code&' +
  'scope=read write');

// 2. Exchange code for token
const response = await fetch('https://auth.example.com/token', {
  method: 'POST',
  body: new URLSearchParams({
    grant_type: 'authorization_code',
    code: authorizationCode,
    client_id: CLIENT_ID,
    client_secret: CLIENT_SECRET
  })
});

Pros: Industry standard, delegated access

Cons: Complex implementation

Use for: Third-party integrations, SSO

mTLS (Mutual TLS)

Both client and server present certificates.

// Nginx mTLS configuration
server {
  listen 443 ssl;

  ssl_certificate /path/to/server.crt;
  ssl_certificate_key /path/to/server.key;

  ssl_client_certificate /path/to/ca.crt;
  ssl_verify_client on;

  location / {
    proxy_pass http://backend;
  }
}

Pros: Strong authentication, encrypted

Cons: Certificate management overhead

Use for: Service-to-service, high-security APIs

API Rate Limiting

// Express rate limiting with Redis
const rateLimit = require('express-rate-limit');
const RedisStore = require('rate-limit-redis');
const Redis = require('ioredis');

const redis = new Redis(process.env.REDIS_URL);

const limiter = rateLimit({
  store: new RedisStore({
    sendCommand: (...args) => redis.call(...args),
  }),
  windowMs: 15 * 60 * 1000, // 15 minutes
  max: 100, // limit each IP to 100 requests per window
  standardHeaders: true,
  legacyHeaders: false,
  message: {
    error: 'Too many requests, please try again later.'
  },
  keyGenerator: (req) => {
    // Rate limit by API key or IP
    return req.headers['x-api-key'] || req.ip;
  }
});

app.use('/api/', limiter);

Data Masking & Tokenization

// Data masking example
function maskCreditCard(cardNumber) {
  // Show only last 4 digits
  return '****-****-****-' + cardNumber.slice(-4);
}

function maskEmail(email) {
  const [local, domain] = email.split('@');
  const maskedLocal = local[0] + '***' + local.slice(-1);
  return `${maskedLocal}@${domain}`;
}

// Tokenization - replace sensitive data with non-sensitive token
const tokenStore = new Map();

function tokenize(data) {
  const token = crypto.randomBytes(16).toString('hex');
  tokenStore.set(token, data);
  return token;
}

function detokenize(token) {
  return tokenStore.get(token);
}

Backup & Recovery

3-2-1 Backup Strategy

  • 3 copies: Original + 2 backups
  • 2 different media: Disk + tape, or cloud + on-premise
  • 1 offsite: Geographic separation for disaster recovery
# Automated backup with encryption
#!/bin/bash

BACKUP_DATE=$(date +%Y%m%d_%H%M%S)
BACKUP_DIR="/backups"
ENCRYPTED_BACKUP="${BACKUP_DIR}/backup_${BACKUP_DATE}.tar.gz.gpg"

# Create backup
tar -czf - /var/lib/postgresql/data | \
  gpg --encrypt --recipient "backup@example.com" > "${ENCRYPTED_BACKUP}"

# Upload to S3 with encryption
aws s3 cp "${ENCRYPTED_BACKUP}" s3://company-backups/db/ \
  --sse AES256

# Verify backup integrity
gpg --decrypt "${ENCRYPTED_BACKUP}" | tar -tzf - > /dev/null

# Retention policy - keep 30 days
find ${BACKUP_DIR} -name "backup_*.tar.gz.gpg" -mtime +30 -delete

Managed service with automatic rotation.

  --name MyDatabaseSecret \
  --secret-string '{"username":"admin","password":"secret"}'

# Retrieve in application
const AWS = require('aws-sdk');
const secretsManager = new AWS.SecretsManager();

const data = await secretsManager.getSecretValue({
  SecretId: 'MyDatabaseSecret'
}).promise();

const secret = JSON.parse(data.SecretString);

Features: Automatic rotation, IAM integration, CloudTrail logging

Environment Variables vs Secrets Managers

Aspect Environment Variables Secrets Manager
Security Low (visible in process list, logs) High (encrypted, access-controlled)
Rotation Manual (requires redeployment) Automatic
Audit None Full audit trail
Complexity Simple Moderate (requires integration)
Cost Free Paid service
Use Case Non-sensitive config Credentials, keys, certificates

Secrets Best Practices

Do's and Don'ts

  • DO: Use secrets managers for all credentials
  • DO: Rotate secrets regularly (90 days)
  • DO: Use different secrets per environment
  • DO: Audit secret access
  • DO: Use short-lived credentials when possible
  • DON'T: Commit secrets to git (use .gitignore)
  • DON'T: Log secrets (sanitize logs)
  • DON'T: Share secrets via email/chat
  • DON'T: Hardcode secrets in application code
  • DON'T: Use default credentials

Threat Modeling

STRIDE Methodology

S - Spoofing

Threat: Pretending to be someone/something else

Example: Identity theft, fake authentication

Mitigation: Strong authentication, MFA, certificates

T - Tampering

Threat: Modifying data or code without authorization

Example: Man-in-the-middle, database manipulation

Mitigation: Integrity checks, digital signatures, checksums

R - Repudiation

Threat: Denying having performed an action

Example: Denying a transaction, false alibis

Mitigation: Audit logging, digital signatures, timestamps

I - Information Disclosure

Threat: Exposing information to unauthorized parties

Example: Data breaches, eavesdropping

Mitigation: Encryption, access controls, data masking

D - Denial of Service

Threat: Making a system unavailable to legitimate users

Example: DDoS attacks, resource exhaustion

Mitigation: Rate limiting, redundancy, auto-scaling

E - Elevation of Privilege

Threat: Gaining unauthorized capabilities

Example: Buffer overflow, privilege escalation

Mitigation: Least privilege, input validation, sandboxing

Threat Modeling Process

1. Define Scope

Identify the system, data flows, trust boundaries, and assets to protect.

2. Identify Threats

Use STRIDE or similar framework to systematically identify threats.

3. Assess Risk

Evaluate likelihood and impact of each threat (risk = likelihood × impact).

4. Define Mitigations

Design controls to address each threat (eliminate, mitigate, transfer, accept).

5. Validate

Review threat model with stakeholders, update as system evolves.

Incident Response

Incident Response Plan

Phase 1: Preparation

  • Define incident response team
  • Establish communication channels
  • Document procedures
  • Train team members
  • Set up monitoring and alerting
  • Conduct tabletop exercises

Phase 2: Detection & Analysis

  • Identify potential security incident
  • Validate the incident
  • Determine scope and impact
  • Classify severity (P1-P4)
  • Document timeline
  • Preserve evidence

Phase 3: Containment

  • Short-term containment (isolate affected systems)
  • Long-term containment (apply patches, change credentials)
  • Eradicate threat (remove malware, close vulnerabilities)
  • Communicate with stakeholders

Phase 4: Recovery

  • Restore systems from clean backups
  • Verify systems are clean
  • Gradually restore service
  • Monitor for recurrence
  • Validate functionality

Phase 5: Post-Incident

  • Conduct lessons learned meeting
  • Document what happened
  • Identify improvements
  • Update policies and procedures
  • File regulatory reports if required

Advanced Security Topics

Zero Trust Architecture

Zero Trust Principles

  • Never trust, always verify: Every access request must be authenticated and authorized
  • Assume breach: Design systems assuming attackers are already inside
  • Least privilege: Grant minimum necessary access
  • Microsegmentation: Isolate workloads to limit blast radius
  • Continuous validation: Re-verify trust throughout session
// Zero Trust access evaluation
async function evaluateAccess(request) {
  const context = {
    user: await authenticateUser(request),
    device: await verifyDevice(request),
    network: await assessNetwork(request),
    resource: await getResource(request),
    action: request.action,
    time: new Date(),
    location: request.geoLocation
  };

  // Continuous risk assessment
  const riskScore = calculateRisk(context);

  if (riskScore > HIGH_RISK_THRESHOLD) {
    await challengeUser(context.user, 'step_up_auth');
  }

  // Policy evaluation
  const allowed = await evaluatePolicy({
    subject: context.user,
    action: context.action,
    resource: context.resource,
    context: context
  });

  if (!allowed) {
    await logAccessDenied(context);
    throw new AccessDeniedError();
  }

  // Establish short-lived session
  return createSession(context, { ttl: '5m' });
}

Privacy-Enhancing Technologies

Differential Privacy

Add noise to data to protect individual privacy while maintaining statistical utility.

// Add Laplace noise for differential privacy
function addNoise(value, sensitivity, epsilon) {
  const scale = sensitivity / epsilon;
  const noise = laplaceDistribution(scale);
  return value + noise;
}

Homomorphic Encryption

Perform computations on encrypted data without decrypting it.

Use case: Privacy-preserving machine learning, secure cloud computing

Limitation: Computationally expensive

Secure Multi-Party Computation

Multiple parties compute a function over their inputs while keeping them private.

Use case: Collaborative analytics, privacy-preserving auctions

Trusted Execution Environments (TEE)

Hardware-based isolation for sensitive computations (Intel SGX, ARM TrustZone).

Use case: DRM, secure enclaves, blockchain

Future Trends

Emerging Technologies

Post-Quantum Cryptography

Quantum computers will break current encryption (RSA, ECC). NIST is standardizing quantum-resistant algorithms.

  • Algorithms: CRYSTALS-Kyber, CRYSTALS-Dilithium
  • Timeline: Migration needed by 2030
  • Action: Start inventorying cryptographic assets

AI-Powered Security

Machine learning for threat detection, automated response, and adversarial AI.

  • Defensive AI: Anomaly detection, behavioral analysis
  • Offensive AI: AI-generated phishing, deepfakes
  • Challenge: AI vs AI arms race

Passwordless Authentication

FIDO2/WebAuthn replacing passwords with cryptographic keys and biometrics.

  • Passkeys: Platform authenticators (iCloud, Google)
  • Benefits: Phishing-resistant, user-friendly
  • Adoption: Growing rapidly (Apple, Google, Microsoft)

Confidential Computing

Protecting data in use with hardware-based isolation (TEEs).

  • Technologies: Intel SGX, AMD SEV, ARM CCA
  • Use cases: Multi-party computation, secure AI
  • Cloud: Azure Confidential VMs, AWS Nitro Enclaves
